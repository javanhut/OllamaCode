# Closing ocode's sandbox gap before tuning

The most valuable change for ocode is not a model-quality tweak. It is closing the sandbox. Network egress is fully open inside the seatbelt and bwrap sandboxes, and the writable workspace includes `.git` and in-repo agent configuration. That combination matches the exploit chain behind most 2025-2026 coding-agent incidents: injected text makes the agent write a file that something trusted later executes, or lets it read a secret and send it out. Second is evaluation. Today's 21-trial suite cannot distinguish gemma4 at 76% from ornith at 86%, so every reliability change is currently untestable. Third, the research supports cheap, deterministic context handling (mask old tool output before summarizing) over more LLM-driven machinery. It also supports per-model edit formats, a ranked repo map in place of default embedding RAG, and a clean agent core that the 17.5k-line TUI package consumes through events. Evidence quality varies. The safety evidence is incident reports and advisories, mostly secondary coverage. The context and verification evidence is mostly frontier or large-model. Almost nothing was measured on 4-30B local models, so most small-model recommendations are inferences and are labeled as such. The roadmap is at the end.

## Evidence strength, and how to read the recommendations

Four tiers of evidence appear below. **Measured** means a controlled result in a paper or study (for example the SWE-agent ablations). **Vendor claim** means an internal or marketing figure (Anthropic's context-editing gains, Morph's apply-model speeds). **Incident or advisory** means a documented real-world failure. **Inference** means the note author's or my reasoning, with no direct measurement. Most measured results come from GPT-4-class, Claude-class or trained 32B models. The notes found no controlled study of sub-14B models for verifier best-of-n, compaction, repo-map retrieval or tool-count effects, and several 2026 arXiv items were seen only as search snippets. Treat those as leads to verify before quoting.

## Open egress and a writable workspace make the sandbox the top risk

The safety notes show a consistent pattern: agents are rarely escaped by breaking the sandbox. They are steered into writing something a trusted component later runs. Copilot's CVE-2025-53773 had injected text write `"chat.tools.autoApprove": true` into `.vscode/settings.json` ([Embrace The Red](https://embracethered.com/blog/posts/2025/github-copilot-remote-code-execution-via-prompt-injection)). Cursor's CurXecute rewrote `.cursor/mcp.json` so a new MCP server ran before the user answered ([Tenable](https://www.tenable.com/blog/faq-cve-2025-54135-cve-2025-54136-vulnerabilities-in-cursor-curxecute-mcpoison)). Pillar's 2026 sandbox-escape series found that git metadata, edited virtualenv interpreters and workspace hook config let unsandboxed tools execute attacker-written files ([BleepingComputer](https://www.bleepingcomputer.com/news/security/cursor-codex-gemini-cli-antigravity-hit-by-sandbox-escapes/)). Claude Code's project-level hooks and settings ran before the trust prompt (CVE-2025-59536, CVE-2026-21852) ([Check Point](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)). ocode's profile (`(allow default)(deny file-write*)` plus writable roots) leaves exactly these paths open. The in-repo instruction files are also the injection surface, so an agent can be told to edit them.

The reference designs are clear. Anthropic's sandbox restricts files and routes all network traffic through a proxy outside the sandbox that enforces a domain allowlist and prompts on new domains, and Anthropic states that without network isolation a compromised agent could exfiltrate SSH keys ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)). Codex defaults network off, makes `.git`, `.codex`, `.agents` and `.aws` read-only even inside writable roots, and blocks private and link-local ranges in its proxy ([OpenAI docs](https://learn.chatgpt.com/docs/agent-approvals-security)). Anthropic reports sandboxing cut permission prompts by 84%, an internal figure, which also means a tight sandbox lowers approval fatigue. For ocode the do-now set is concrete: add `(deny network*)` on seatbelt and `--unshare-net` on bwrap by default; make `.git/hooks`, `.git/config` and any gitdir pointer, ocode config, rules, hooks and MCP definitions, `.vscode`, `.claude` and `.cursor` read-only inside the writable root; deny reads of `~/.ssh`, `~/.aws`, `~/.gnupg`, keychains and other agents' config directories; deny the Docker socket; and start subprocesses with an allowlisted environment that strips `*_TOKEN`, `*_KEY` and `SSH_AUTH_SOCK`. These are implementation inferences from the incident record, not measured effects. A domain-allowlist proxy for package registries is the follow-on, with the caveat that allowlists have their own holes: an allowlisted package proxy was reportedly used to escape a network-isolated sandbox in a GitLab evaluation (vendor-reported) ([InfoQ](https://infoq.com/news/2026/09/gitlab-ai-sandbox-access)), and DNS tools like `dig` leaked data from Claude Code's safe list (CVE-2025-55284) ([Embrace The Red](https://embracethered.com/blog/posts/2025/claude-code-exfiltration-via-dns-requests)).

The second gap is the shell rule matcher. ocode splits compound commands with a custom splitter rather than a real parser. Every shipped agent in the notes had an allowlist bypass: Claude Code's `echo` and `sed` parsing bugs (CVE-2025-54795, CVE-2025-64755, CVE-2026-25723) ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-25723)), Gemini CLI's prefix match that let a chained command ride along ([Tracebit](https://tracebit.com/blog/code-exec-deception-gemini-ai-cli-hijack)), and Codex trusting `git show` by name rather than arguments. The recommended pattern is a real AST parser that rejects on parse error or unknown node type, checks each command's argv rather than its name, and executes through an explicit `bash --noprofile --norc -c` so parser and executor agree. mvdan/sh is the natural Go choice, though the notes found no example of it in agent permission code, and the Claude Code internals come from an unofficial source dump. The notes' own conclusion is the right framing: treat the allowlist as UX and the sandbox as the boundary.

Beyond the sandbox, three policy changes follow from the record. Project config must be inert until the user trusts the directory, and MCP trust should be pinned to a hash of command, args, env and tool descriptions, because Cursor's MCPoison bound trust to the entry name and was defeated by a later swap ([Check Point](https://research.checkpoint.com/2025/cursor-vulnerability-mcpoison/)). A session-level taint flag, set after web fetch, MCP results or untrusted files, should downgrade session and always approval scopes to per-call for network, config and out-of-workspace actions; this implements Meta's Agents Rule of Two ([Meta](https://ai.meta.com/blog/practical-ai-agent-security/)) and Willison's lethal trifecta ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)) with structure instead of detection. Detection is a poor primary defense: adaptive attacks bypassed all 12 evaluated prompt-injection defenses at over 90% success ([arXiv 2510.09023](https://arxiv.org/abs/2510.09023)). No data exists on how small local models resist injection compared with frontier models; it is plausible they are weaker, but that is unsourced. Dream mode deserves its own policy because no source covers idle agents. The nearest evidence is CI agents leaking `GITHUB_TOKEN` and API keys through injected issue and PR text ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-comment-control-github-prompt-injection-20/)), and Gemini CLI's `--yolo` ignoring its tool allowlist in headless mode (GHSA-wpqr-6v78-jr5g) ([The Hacker News](https://thehackernews.com/2026/04/google-fixes-cvss-10-gemini-cli-ci-rce.html?hl=en)). The inferred posture: read-only, no network, no MCP or web fetch, ask-type permissions fail closed, and output restricted to a proposals file that is not auto-loaded as instructions on the next run (persistent memory poisoning is the risk).

## A 21-trial suite cannot support any of the comparisons ocode wants to make

The 16/21 versus 18/21 gap is not a finding. By the standard binary-score formula, SE is sqrt(p(1-p)/n) and the 95% interval is plus or minus 1.96 SE ([arXiv 2411.00640](https://arxiv.org/html/2411.00640v1)). My arithmetic gives roughly plus or minus 18 and 15 points for the two arms and an unpaired difference z of about 0.8, and this ignores that three trials of one task are correlated, so effective n is nearer 7. The notes' own estimate is a minimum detectable effect near 34 points unpaired at 21 trials. Agentic run-to-run noise is also larger than people assume: single-run pass@1 on SWE-bench Verified spans 2.2-6.0 points with standard deviation 0.7-1.8, and temperature 0 is not deterministic ([arXiv 2602.07150](https://arxiv.org/html/2602.07150v2)). One model moved from 20.4% at T=0 to 31.4% at T=1.0 in the same study, so sampling settings can swamp a harness change. The "constrained decoding showed no change for ornith" result is therefore only weakly informative, and the corrupt gemma4 constrained file leaves the more interesting arm unmeasured. Re-run it first.

The method fix is well established. Grow to 50-100 tasks with 3-5 trials, compare variants on identical tasks, bootstrap over tasks, report per-task flips beside pass rates, and report pass^k (all k trials succeed) next to pass@1, because consistency is what users feel: a 75% trial rate gives about 42% at pass^3 ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Pin model, quantization, temperature and seed in every result file. Gate CI on a bound or a large margin, not a point estimate. Anthropic's practical advice is 20-50 tasks drawn from real failures, each with a reference solution, and treating near-0% across many trials as a broken grader ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). ocode already has the best input for this, namely redacted traces with promote-to-fixture. Add a validity check per fixture (fails on base, passes with the fix, a mutated wrong solution fails) and mine the repo's own history for test-plus-source commits. The notes call that source an inference, since no paper describes it for small repos. Programmatic bug-injection in the SWE-smith style gives cheap volume, but those tasks skew easy and suit regression more than headline capability ([arXiv 2504.21798](https://arxiv.org/abs/2504.21798)).

Two design points need care. The "ordered tool calls" check is exactly the rigid step grading Anthropic warns penalizes valid solutions, so keep ordering only for true contracts such as read-before-edit and make everything else outcome-based. And public benchmarks are poor targets: OpenAI stopped reporting SWE-bench Verified after finding 59.4% of the audited hard problems had material test or description flaws ([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)), SWE-bench Pro drew an audit flagging roughly 30% of tasks as broken ([OpenAI](https://openai.com/blog/separating-signal-from-noise-coding-evaluations), via search summary; the withdrawal date comes from a weak source), and Terminal-Bench scores sit near 15% for smaller models, leaving no room to see deltas ([arXiv 2601.11868](https://arxiv.org/html/2601.11868v1)). The notes suggest Aider polyglot (225 tasks, cheap unit-test grading), a slice of SWE-rebench, and BFCL-style format checks as secondary signals. That use on local models is the note author's judgment, and no Ollama results were found. Harness choice moves results meaningfully on the same model (one report 69.7% to 77.0%) ([arXiv 2605.23950](https://arxiv.org/html/2605.23950), snippet-level), which justifies the investment, and implies a bash-only baseline mode in the eval, as mini-SWE-agent does ([docs](https://mini-swe-agent.com/latest/)), to measure what each custom tool earns per local model.

## Small-model reliability: lenient edits and per-model profiles beat more constraint

ocode already has the main reliability ladder (salvage, did-you-mean, text-emitted calls, schema re-ask, tiered edit matching, syntax refusal, LSP diagnostics). The research mostly validates it and points at refinements. On constrained decoding, the best evidence says constraint can hurt reasoning when applied to the whole output: Tam et al. found JSON mode usually worst on reasoning tasks and proposed reasoning freely, then structuring ([arXiv 2408.02442](https://arxiv.org/abs/2408.02442v2)), while JSONSchemaBench found gains of up to 4% when schemas are well covered ([arXiv 2501.10868](https://arxiv.org/html/2501.10868v3)). Aider's JSON-wrapped-code finding points the same way ([Aider](https://aider.chat/2024/08/14/code-in-json.html)). No agentic-coding measurement of constrained tool calls on small models exists. ocode's observed null result for ornith is consistent with keeping constraint as a retry fallback only, with flat schemas and few optional parameters, since llama.cpp reports show tool-call degradation with many optional parameters at long context ([llama.cpp #19382](https://github.com/ggml-org/llama.cpp/issues/19382), snippet-level). The right test is a paired code-quality comparison, not tool-call validity.

Edit format is model-dependent. Diff-XYZ found search-replace best for larger models and modified udiff variants better for smaller ones, with small open models weak across all formats ([arXiv 2510.12487](https://arxiv.org/html/2510.12487v2)). Aider (GPT-4-era, old) found disabling flexible patch application caused 9x more editing errors ([Aider](https://aider.chat/docs/unified-diffs.html)), which supports ocode's tiered matcher; SWE-Edit trained Qwen3-8B to choose between find-replace and whole-file rewrite for a 12.5-point edit-success gain ([arXiv 2604.26102](https://arxiv.org/html/2604.26102)). Two harness-level inferences follow: a per-model edit-format setting, and an automatic whole-file fallback for small files after N failed matches. SWE-agent's trajectory data shows why the fallback matters: after one failed edit, eventual edit success fell from 90.5% to 57.2% ([arXiv 2405.15793](https://arxiv.org/html/2405.15793v3), GPT-4 Turbo). Apply models such as Morph claim 96-98% accuracy at thousands of tokens per second, but these are vendor numbers with no independent benchmark and would add a second model call, so skip them.

Runtime format mismatch is a separate and well-documented failure source. Qwen3-Coder emits an XML-style tool call, and Hermes-style parsers silently drop calls ([llama.cpp #15012](https://github.com/ggml-org/llama.cpp/issues/15012)); gpt-oss needs the native Harmony format with reported parse failures ([arXiv 2604.00362](https://arxiv.org/pdf/2604.00362)). ocode's text-emitted-call parsing is the right defense. Extend the per-model profile (which already supplies num_ctx) with tool-call format and recommended temperature (Mistral recommends 0.2 for Devstral Small 2) ([Mistral](https://mistral.ai/news/devstral-2-vibe-cli/)), and log a counter of silently dropped calls. For context selection, Aider's repo map (tree-sitter definitions, PageRank personalized to chat files, binary-searched to a token budget of roughly one-eighth of context) is the proven cheap design ([DeepWiki](https://deepwiki.com/Aider-AI/aider/4.1-repository-mapping), secondhand), and Agentless showed structural localization is competitive with full agents at a fraction of the cost ([arXiv 2407.01489](https://arxiv.org/html/2407.01489v2)). Against ocode's embedding-based auto-RAG, the notes find practitioner preference for grep/glob search (Claude Code's Boris Cherny, mostly informal evidence, secondary summary) ([OfficeChai](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/)) and a counterpoint that semantic search helps on repos of 1,000+ files ([AI Engineer talk](https://ai.engineer/talks/UM6sFg_jdlE-rag-is-dead-right-kuba-rogut), snippet-level). No controlled comparison exists for small models, so the decision belongs to ocode's eval: A/B auto-RAG on and off, and a repo-map variant using LSP symbols where tree-sitter queries are missing. Tool count is the same kind of open question: retrieval-filtered tool exposure raised tool-selection accuracy from 13.6% to 43.1% in RAG-MCP ([arXiv 2505.03275](https://arxiv.org/abs/2505.03275)), but model sizes were not verified, so treat large MCP tool lists as a risk and expose tools by mode, which ocode already does.

### Verification and self-repair: external signals work, so tighten the loop rather than add critics

The verification gate, LSP feedback, targeted tests and loop guards already match the best-evidenced practice. Lint-gated edits gave a measured 3 points on SWE-bench Lite (18.0% versus 15.0%) ([arXiv 2405.15793](https://arxiv.org/html/2405.15793v3)), and a 2026 system reports its compile gate adding 7.2 points ([EviACT](https://arxiv.org/pdf/2605.27238), snippet-level). Self-repair gains are modest and depend on feedback quality; models fix errors shown by an external source far better than their own ([Olausson et al.](https://arxiv.org/abs/2306.09896), [arXiv 2507.02778](https://arxiv.org/abs/2507.02778)). Consistent with that, the notes suggest three small additions. Cap consecutive same-kind failures at about 2-3 and then change strategy (re-read, checkpoint reset, or ask the user); the cap value is inferred from SWE-agent's recovery curve, and no source gives an optimum. Add a "same compile error N times" stuck signal, which an OpenHands mirror also uses ([mirror](https://huggingface.co/spaces/Backup-bdg/OpenHands/raw/main/openhands/controller/stuck.py), unofficial). And warn, not block, when a turn deletes or weakens tests, adds skip or xfail markers, or edits conftest or CI config. Reward hacking is documented in frontier models, with o3 hacking every trajectory on one RE-Bench task ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)), and a model-added `conftest.py` can rewrite pytest outcomes ([arXiv 2605.12673](https://arxiv.org/html/2605.12673), snippet-level). Whether small local models do this is unmeasured, so the guard is cheap insurance. Because the gate runs project tests rather than trusting the agent's claim, ocode already avoids the main trap.

Best-of-n with verifiers shows real gains for 32B-class trained systems (a verifier on SWE-Gym rollouts gives roughly log-linear improvement in k) ([arXiv 2412.21139](https://arxiv.org/html/2412.21139v2)). R2E-Gym found a hybrid of execution-based and execution-free selection beat either alone, and each plateaued near 43% ([arXiv 2504.07164](https://arxiv.org/html/2504.07164v1)). The notes found nothing for sub-14B models. A cheap version for ocode, itself an inference, is restart-from-checkpoint with a fresh sample after the retry cap, keeping the candidate that passes build, tests and LSP. Writing a failing test first has no measured single-trajectory benefit; TestPrune-style relevant-test selection improved patch selection by 9.4-12.9% relative ([arXiv 2510.18270](https://arxiv.org/abs/2510.18270)), which supports ocode's changed-path-aware targeting.

## Context: mask first, summarize second, and treat nominal windows skeptically

ocode already sets num_ctx per request, keeps a byte-stable prefix, spills large outputs to files and compacts at 80%. The strongest controlled finding in the notes bears on the next step. JetBrains' study across five configurations on SWE-bench Verified found observation masking halved cost versus the raw agent and matched or slightly beat LLM summarization (about 52% cost cut and +2.6 points for the best model); observations were about 84% of an average turn's tokens, and a hybrid saved a further 7-11% ([arXiv 2508.21433](https://arxiv.org/abs/2508.21433)). Those are API-scale models in SWE-agent. The recommended design is a deterministic prune tier before any LLM summary, in the style of opencode's pruning, which protects the most recent roughly 40k tokens of tool output and stubs older ones with a path (third-party write-up) ([gist](https://gist.github.com/sam-saffron-jarvis/2c8a6c26297f5748dac55b597381d268)). It costs no local inference, which is slow, and ocode's existing spill-to-file already supplies the restorable stub. Extending the same "re-read path X" stub to old `read_file` and `grep` results is the main gap the notes identify. Anthropic's context-editing results (+29% on an internal agentic-search eval, +39% with the memory tool) are vendor claims whose evals are not described in detail ([Claude blog](https://claude.com/blog/context-management)). A caution on latency: across about 35,000 runs of three open-weight models, policies using a third of the tokens took 20-80% longer on Terminal-Bench with Qwen, so measure wall time, not tokens ([arXiv 2609.32961](https://arxiv.org/abs/2609.32961), snippet-level).

The 80% trigger is likely too late for small models. Chroma's study of 18 models including Qwen3-8B found quality falls as input grows even on simple tasks ([Chroma](https://www.trychroma.com/research/context-rot)), and NoLiMa found Llama 3.1 8B had an effective length near 1K on its benchmark despite a 128K claim ([arXiv 2502.05167](https://arxiv.org/html/2502.05167v3)). Those tests are not coding tasks, so the conclusion is an inference: add a per-model soft threshold (mask at roughly 40-50%, summarize at 70-80%) and tune it in the eval. Summaries should be structured around what later steps need (paths, failing tests, decisions, open errors), because compaction scored on the current question does not reliably predict usefulness for later ones ([arXiv 2610.27301](https://arxiv.org/abs/2610.27301), snippet-level). Two cache checks are cheap. First, confirm the volatile tail is stable between consecutive turns when unchanged; llama.cpp prefix reuse breaks from the first changed token ([Schmalbach](https://www.vincentschmalbach.com/why-llamacpp-reprocesses-the-whole-prompt-after-every-tool-call-and-how-to-keep-the-kv-cache-warm/), secondary), and any history rewrite should be batched at compaction boundaries rather than every turn (Manus's append-only rule) ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Second, since num_ctx is already set, add a guard that compares `prompt_eval_count` to it and warns on near-limit prompts, because the notes found no authoritative description of Ollama's truncation behavior and Ollama's own docs say agentic tools should use at least 64k ([Ollama docs](https://docs.ollama.com/context-length)). Whether `prompt_eval_count` reliably reveals truncation is unverified; test it.

Memory and dream mode should be pruned toward less, not more. ETH Zurich found LLM-generated context files changed success by about -0.5% to -2% (non-significant) while raising cost 20-23%, and human-written files gave about +2.4% (non-significant) at up to 19% more cost ([arXiv 2602.11988](https://arxiv.org/html/2602.11988)). The implication for dream-mode reflection is to prefer deduplication and pruning, store only non-obvious conventions, failed commands and user preferences, inject under a token cap, and A/B test memory on and off. Plan recitation (a short todo at the tail) and keeping error text in context are Manus practices with no ablation, so adopt them only through the eval. Subagents are best kept as read-only, context-isolating investigators returning short results; Anthropic's 90.2% multi-agent gain is for research, not coding, and the same post calls most coding tasks a poor fit ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). On a single local GPU, parallel subagents serialize, so the benefit is isolation, not speed (inference).

## Architecture: finish the agent core split and demote what the evidence disfavors

The industry pattern in the notes is a UI-agnostic loop emitting typed events with TUI, headless, IDE and eval as peer clients. Claude Code's surfaces share one query loop ([arXiv 2604.14228](https://arxiv.org/html/2604.14228v1), a source study), Codex's app-server exposes thread, turn and item primitives with server-initiated approval requests ([Codex docs](https://learn.chatgpt.com/docs/app-server)), and OpenHands V1 emits events through an on_event callback with local and remote conversations ([arXiv 2511.03690](https://arxiv.org/html/2511.03690v2)). ocode has the seed in `internal/agent` (a headless loop, a shared executor, a parity test) but the 17.5k-line TUI Model still mixes agent logic with view state. The concrete move: define `Session`, `Event` and `Command` types; make approvals a request/response pair on the event stream so headless and eval apply a policy where the TUI asks a human; and move mode, routing, the verification gate and checkpoints into core as middleware. Persist an append-only JSONL log as the single source of truth for resume, replay, eval and LoRA export. OpenHands measured about 0.20 ms median per event persist and 7.4 ms crash recovery on 433 conversations. The payoff is also in safety: the parity test already guarding the shared executor is the right place to assert that deny rules, the taint policy and sandbox settings apply identically in TUI, headless, subagents and dream mode, the exact class of bug behind Gemini CLI's `--yolo` advisory.

On sprawl, the evidence supports specific demotions, with the caveat that no source tested them on local models. Cognition's 2026 guidance is that multi-agent systems work when writes stay single-threaded and extra agents contribute intelligence, not actions ([Cognition](https://cognition.com/blog/multi-agents-working)), which makes `parallel_edit` the clearest candidate to make opt-in or remove; the notes could not tell how ocode uses it, so weigh against its eval results. Auto-RAG as a default, and model routing, should each earn their place through the paired eval above. Voice, LoRA export, guided research and dream mode have no analogue in the harnesses surveyed, so move them behind hooks, MCP or separate binaries consuming the event protocol. mini-SWE-agent's claim that a 100-line bash-only agent scores over 74% on Verified is self-reported and depends on frontier models, so it does not transfer directly to small ones, where tool design plausibly matters more ([docs](https://mini-swe-agent.com/latest/)). An `ocode acp` stdio adapter is an inexpensive editor-distribution bet after the core split, since ACP has traction across Zed, JetBrains and others ([Zed](https://zed.dev/acp), mostly partner sources); check for an official Go library first. Fine-tuning on harness trajectories has support, since 5,016 verified trajectories took Qwen2.5-Coder-32B to 40.2% on Verified in SWE-smith ([arXiv 2504.21798](https://arxiv.org/abs/2504.21798)), so make the LoRA exporter keep only runs that pass tests and are LSP-clean.

## Conclusion

The notes change the order of operations. The usual instinct for a local-model harness is to improve the model-facing layer (better parsing, more constraint, smarter retrieval). The evidence says that layer is already close to what published designs do, and that its remaining gains cannot be seen with 21 trials. The largest unforced risk is on the other side: a permissive sandbox and writable in-repo config in a tool that reads untrusted repo text. The largest process gap is measurement. Fixing those two makes every later change either safe or testable.

Several decisions are real open questions, not recommendations. Whether embedding RAG, model routing, parallel_edit and dream-mode memory earn their cost for 4-30B models has no published answer, and ocode's own paired eval, with a bash-only baseline, is the only way to find out. The same applies to the lower compaction thresholds and to constrained decoding. Treat the inferences in this report as hypotheses for that eval, and treat the safety items as defaults that do not need one.
